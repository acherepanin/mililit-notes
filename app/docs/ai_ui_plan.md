# План Следующих Этапов Notes AI

## Назначение

Документ фиксирует только незавершенные AI-направления. Реализованный MVP Notes AI описан в `functionality.md`, `architecture.md`, `api.md` и `bot_setup.md`; здесь не дублируем закрытые пункты.

Все новые AI-возможности должны оставаться в отдельном AI-модуле:

- backend: `AiModule`, `AiService`, `AiToolsService`, bot runtime и отдельные `ai_*` таблицы;
- frontend: `features/ai` и существующие общие UI-компоненты;
- новые действия модели добавляются через tool registry, а не прямым доступом к БД;
- любые изменения tool API, UI-сценариев и прав обязательно дублируются в developer prompt Notes AI.

## 1. Расширенные AI-Функции Вне Текущего Tool Registry

Статус: **не сделано**.

Сейчас Notes AI работает только через существующий registry tools: поиск, чтение, создание, редактирование, вложенное batch-создание, удаление, восстановление, теги, избранное, закрепление, шаблоны, версии, вложения, share links и admin-only чтение.

Нужно спроектировать расширяемый набор возможностей, которые пока не входят в tool registry:

- интеллектуальная реорганизация дерева заметок;
- массовая нормализация названий и структуры;
- генерация структуры проекта/инструкции из свободного текста;
- поиск дублей и похожих заметок;
- объединение нескольких заметок в одну;
- разбиение большой заметки на несколько вложенных;
- анализ устаревших данных;
- предложения по тегам, закреплению и архивированию на уровне всего аккаунта;
- безопасная работа с секретами в сложных сценариях без раскрытия лишних значений.

Требования:

- каждое действие оформлять отдельным tool-call;
- каждый tool должен иметь строгий payload и server-side validation;
- опасные действия должны идти через preview/confirmation;
- действия должны проверять `user_id`, ownership, роль и bot permissions;
- backend не должен парсить смысл задачи вместо LLM, но должен валидировать результат;
- результаты должны быть понятны UI и ботам.

Критерии готовности:

- описан список новых tools;
- для каждого tool есть payload schema;
- обновлен developer prompt Notes AI;
- обновлены `api.md`, `architecture.md`, `functionality.md`;
- добавлены проверки на лимиты, ownership и ошибки provider/tool-call.

## 2. Обработка Вложений Прямо Из Telegram/VK

Статус: **не сделано**.

Сейчас Telegram/VK runtime принимает текст и голосовые сообщения. Файлы, изображения, документы и архивы из мессенджеров не загружаются в файловый менеджер аккаунта и не анализируются Notes AI.

Нужно добавить прием вложений из Telegram/VK:

- изображения;
- документы;
- текстовые файлы;
- PDF;
- архивы, если это безопасно;
- конфиги и `.env` файлы;
- несколько вложений в одном сообщении;
- подпись к вложению как текстовую команду.

Ожидаемый поток:

1. Бот получает сообщение с вложениями.
2. Runtime проверяет, что внешний аккаунт привязан.
3. Runtime проверяет user bot permissions на файлы и запись.
4. Runtime скачивает файл только по HTTPS.
5. Backend проверяет размер, MIME type, расширение и лимиты.
6. Файл сохраняется через существующий `WorkspaceService`.
7. Если в сообщении есть команда, Notes AI получает контекст загруженных файлов.
8. Модель может привязать файл к заметке, создать заметку по файлу или вернуть короткий ответ.

Безопасность:

- не скачивать файлы без привязанного аккаунта;
- не сохранять файл, если нет прав на вложения;
- не отправлять содержимое файла в LLM без явного сценария;
- ограничить размер и количество файлов;
- не писать содержимое файлов, секреты и токены в logs/audit;
- для неподдерживаемых файлов возвращать понятное сообщение.

UI/UX:

- в настройках ботов добавить флаг доступа к загрузке вложений, если текущего права `Файлы` недостаточно;
- в истории/статистике показывать количество загруженных через ботов файлов;
- в ответе бота писать, куда файл сохранен и к какой заметке привязан.

Критерии готовности:

- Telegram attachments сохраняются в файлы аккаунта;
- VK attachments сохраняются в файлы аккаунта;
- можно привязать файл к заметке командой в чате;
- ошибки загрузки не ломают обработку сообщения целиком;
- документация содержит инструкции и ограничения.

## 3. Отдельные Provider-Specific Adapters

Статус: **не сделано**.

Сейчас Notes AI использует единый OpenAI-compatible gateway: `GET /models`, `POST /chat/completions`, `POST /embeddings`, `POST /audio/transcriptions`. Это покрывает совместимых провайдеров, но не учитывает отличия конкретных API.

Нужно добавить adapter layer для provider-specific поведения без изменения frontend и tool registry.

Потенциальные adapters:

- OpenAI;
- OpenRouter;
- Groq;
- DeepSeek;
- Mistral;
- Qwen;
- Custom OpenAI-compatible.

Что должен уметь adapter:

- нормализовать список моделей;
- определять capabilities модели;
- выбирать endpoint для chat/completions или альтернативный endpoint;
- нормализовать provider errors;
- нормализовать token usage;
- поддерживать embeddings, если provider имеет отдельную схему;
- поддерживать audio transcription, если provider имеет отдельную схему;
- корректно помечать unsupported features;
- отдавать единый internal response в `AiService`.

Требования к архитектуре:

- frontend не должен знать provider-specific детали;
- tool registry не должен знать provider-specific детали;
- `AiService` должен выбирать adapter по `providerName/baseUrl`;
- fallback adapter остается OpenAI-compatible;
- provider-specific код не должен размазываться по сервисам.

Критерии готовности:

- есть общий интерфейс adapter;
- OpenAI-compatible adapter вынесен как default;
- минимум один provider-specific adapter реализован и проверен;
- ошибки provider приводятся к единому формату;
- документация описывает, чем adapter отличается от preset.

## 4. Новые Специализированные AI Tools Под Сложные Сценарии

Статус: **не сделано**.

Часть сложных пользовательских команд нельзя надежно выполнять набором мелких tools, потому что модель может потерять контекст, выбрать не все id или сделать лишние промежуточные поиски. Для таких сценариев нужны отдельные tools с четкой серверной логикой.

Кандидаты на новые tools:

- `notes.merge` - объединить несколько заметок в одну;
- `notes.split` - разделить текущую заметку на несколько дочерних;
- `notes.moveBatch` - массово переместить заметки;
- `notes.renameBatch` - массово переименовать по шаблону;
- `notes.tagBatch` - массово назначить/снять теги;
- `notes.findDuplicates` - найти похожие или одинаковые заметки;
- `notes.archiveBatch` или аналог через корзину/теги, если будет добавлен архив;
- `attachments.summarize` - подготовить краткое описание файла, если file-to-LLM будет разрешен;
- `workspace.cleanupSuggestions` - предложить безопасную уборку дерева без автоматического выполнения.

Правила проектирования:

- tool должен решать один понятный сценарий;
- payload должен быть компактным и валидируемым;
- bulk tools должны иметь лимиты;
- destructive tools должны быть marked destructive;
- результат должен возвращать ids затронутых сущностей;
- UI должен обновлять дерево/выбранную заметку после выполнения;
- bot runtime должен уметь ограничивать эти tools отдельными permissions.

Критерии готовности:

- выбран список tools для следующего релиза;
- для каждого tool есть описание use cases;
- реализованы backend methods без дублирования existing services;
- developer prompt объясняет, когда выбирать новый tool;
- docs и API примеры обновлены.

## 5. Более Глубокая Работа С Внешними Чатами И Ограничением Chat/User ID

Статус: **не сделано**.

Сейчас привязка Telegram/VK работает на уровне внешнего аккаунта пользователя и bot permissions. Более тонкая политика доступа по конкретным chat id, user id, group chat и allowed dialogs пока не реализована как полноценный UI-сценарий.

Нужно добавить гибкое ограничение внешних чатов:

- список разрешенных Telegram chat id;
- список разрешенных Telegram user id, если нужно отделять личку от групп;
- список разрешенных VK peer id/user id;
- режим `только личные сообщения`;
- режим `личные + выбранные группы`;
- запрет выполнения mutation-действий в групповых чатах;
- отдельное подтверждение опасных действий в группе;
- audit привязки внешнего chat id к действию.

Ожидаемый UX:

- пользователь видит подключенный Telegram/VK аккаунт;
- рядом отображаются последние замеченные чаты без раскрытия лишнего содержимого;
- пользователь может включить/выключить доступ для конкретного чата;
- можно быстро выбрать безопасный режим `только личные сообщения`;
- tooltip объясняет, что chat id не является паролем, но ограничивает поверхность доступа.

Backend:

- хранить allowlist в отдельной `ai_bot_allowed_chats` таблице или JSON-поле, если объем маленький;
- проверять allowlist до вызова LLM;
- не создавать pending action, если чат запрещен;
- логировать отказ без содержимого сообщения;
- предусмотреть миграцию и обратную совместимость.

Критерии готовности:

- Telegram личные/групповые чаты различаются;
- VK peer/user ограничения работают;
- запрещенный чат получает короткий отказ;
- разрешенный чат работает как раньше;
- UI позволяет управлять списком без ручного редактирования БД;
- документация описывает настройку и риски.

## Общие Правила Для Следующих Этапов

Статус: **актуально**.

- Любой новый AI tool добавляется в `AiToolsService`.
- Любое новое действие добавляется в developer prompt Notes AI.
- Любой новый bot-доступ добавляется в permission matrix.
- Любая новая внешняя интеграция должна работать через backend, а не через frontend.
- Секреты и API keys не возвращаются в UI в открытом виде.
- Все ошибки идут через существующий toast/alerting.
- Все tooltips/popups используют общий portal-layer.
- Документация обновляется вместе с кодом.
- После каждой доработки выполняется build frontend и backend.
